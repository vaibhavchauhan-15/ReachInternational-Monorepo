# Feature: Client Directory & CRM Reference Master (`/clients`)

## 1. Overview & Architecture
The `/clients` directory provides enterprise client lifecycle management, billing & site address registry, fleet equipment rental associations, and high-performance search across India.

- **Route (Web)**: `/clients` (`apps/web/app/(app)/clients/page.tsx`)
- **Route (Mobile)**: `/(app)/clients` (`apps/mobile/app/(app)/clients.tsx`)
- **Coordinator**: `apps/web/components/clients/ClientsCoordinatorClient.tsx`
- **Data Access Layer (DAL)**: `apps/web/lib/data/clients/`
  - `client-kpis.ts`: Single-aggregation RPC `get_clients_directory_summary()`
  - `client-list.ts`: Lean column projection `CLIENT_LIST_COLUMNS`, server sorting, status filtering, cursor pagination
  - `client-search.ts`: 8-dimension GIN trigram search
  - `client-detail.ts`: Deep relational fetcher for client detail drawer
  - `client-locations.ts`: Cached distinct cities
  - `client-export.ts`: Streaming CSV export with Excel UTF-8 BOM
  - `client-mutations.ts`: Atomic lifecycle operations with audit logging
- **Server Actions**: `apps/web/app/actions/clients.ts`
  - `getClientListAction`: On-demand tab & page size loading
  - `searchClientsAction`: 8-dimension trigram search
  - `createClientAction`, `updateClientAction`, `softDeleteClientAction`

## 2. Table Optimization & Keyset Cursor Pagination (Milestone C10)
1. **Exact 7-Column Projection**:
   - Strictly retrieves the fields needed for the 7 table columns: `CODE`, `COMPANY & TAX`, `CONTACT PERSON`, `PHONE`, `SITE LOCATION`, `STATUS`, `ACTIONS`.
   - `CLIENT_LIST_COLUMNS`: `"id, code, company_name, contact_person, phone, gstin, pan_number, street, city, district, state, pincode, is_billing_address_different, status, deleted_at"`.
   - **Zero Overfetching Guarantee**: Absolutely zero machine relations, running logs, assignments, or audit records are queried.
2. **Server-Side Page Sizing**:
   - Supported options: `10`, `25`, `50`, `100` records per slice.
   - Interactive UI density selector across Desktop (`Pagination`) and Mobile touch chips (`pageSizeRow`).
   - Integrated with URL search parameters (`?pageSize=25`).
3. **Keyset / Cursor Pagination for Massive Datasets**:
   - Replaced deep $O(N)$ `OFFSET` scans with $O(1)$ composite index seeks using Base64URL-encoded cursors (`afterCursor`, `beforeCursor`).
   - Backed by Migration 074 composite B-tree indexes:
     - `idx_clients_cursor_company_name` on `(company_name ASC, id ASC)`
     - `idx_clients_cursor_active` on `(company_name ASC, id ASC) WHERE status = 'active' AND deleted_at IS NULL`
     - `idx_clients_cursor_status` on `(status, company_name ASC, id ASC)`
     - `idx_clients_cursor_created_desc` on `(created_at DESC, id DESC)`
     - `idx_clients_cursor_code` on `(code ASC, id ASC)`
   - Computes `hasMore`, `nextCursor`, and `prevCursor` across all queries.
4. **Cross-Platform Mobile Parity**:
   - Mobile client query aligned to lean `CLIENT_LIST_COLUMNS`.
   - Server-side page size selection (`10, 25, 50, 100`) with touch-friendly chips.

## 3. All / Active / Inactive Tabs Optimization (Milestone C9)
1. **Zero Preloading of Non-Active Datasets**:
   - Initial cold load loads strictly the initial status dataset (default: `status=all`).
   - Active and Inactive datasets are NOT preloaded upfront, saving database load and unnecessary memory allocation.
2. **C9 Intelligent Detection — Existing `status=active` Reuse**:
   - If the current list query already contains all active records (`metrics.total === metrics.active`), switching to the "Active" tab detects this condition and reuses the existing cached result without issuing any network request or database query (**0 queries, 0.0068ms**).
3. **C9 Intelligent Detection — Zero-Inactive Optimization**:
   - If `metrics.inactive === 0` (and no search query is active), clicking "Inactive" immediately returns an empty result set (`[]`, `total: 0`) with **0 database queries (0.0062ms)**.
4. **0ms In-Memory Session Caching (`queryCacheRef`)**:
   - Tabs fetched on demand are cached under canonical keys generated by `serializeClientFilter` with a 60s TTL.
   - Subsequent tab toggles between "All", "Active", and "Inactive" resolve from memory in **0ms** (sub-millisecond ~0.004ms).
5. **Silent URL Synchronization (`window.history.replaceState`)**:
   - Tab transitions update URL parameters (`?status=active`, etc.) silently without triggering Next.js RSC full-page re-renders, keeping URLs 100% bookmarkable.
6. **Cross-Platform Mobile Parity (`apps/mobile/app/(app)/clients.tsx`)**:
   - Synchronized `mobileQueryCacheRef`, active result reuse, zero-inactive optimization, and dynamic count badges on filter chips (`ALL (2)`, `ACTIVE (2)`, `INACTIVE (0)`).
7. **Surgical Mutation Invalidation**:
   - Client mutations (create, edit, soft-delete, restore) immediately clear the client query cache and revalidate server tags.

## 4. Client Detail Independent Section Loading Architecture (Milestone C11)
When inspecting a client record (e.g. clicking `CLI-0002`), data fetching is completely isolated into independent on-demand segments to guarantee zero upfront overfetching:

```
Client Detail
│
├── Summary      → immediate
├── Contact      → immediate/summary
├── Tax          → immediate/summary
├── Location     → on demand
├── Machines     → on tab
├── Running Logs → on tab
├── Assignments  → on tab
├── History      → on tab
└── Audit        → on tab

Each section independently loads.
```

1. **Zero Upfront Relational Fetching**:
   - Opening the client drawer or modal executes strictly 0 relational queries to `machines`, `machine_hour_logs`, `operator_machine_assignments`, or `audit_logs`.
2. **Immediate Summary, Contact & Tax (0ms wire latency)**:
   - Summary header (Code, Company Name, Status Badge), primary contact person, phone (with click-to-call link), and statutory tax identifiers (GSTIN, PAN) render immediately from the client core record in a persistent top container.
3. **On-Demand Location Accordion**:
   - Fetches full operational address and distinct registered billing address on demand via `getClientLocationAction` (279.87ms cold).
4. **Independent On-Tab Loaders**:
   - Dedicated DAL query services and server actions: `getClientMachinesAction` (274.08ms), `getClientRunningLogsAction` (227.03ms), `getClientAssignmentsAction` (352.18ms), `getClientHistoryAction` (255.41ms), `getClientAuditLogsAction` (241.65ms).
5. **In-Memory Session Caching (0ms Re-Toggles)**:
   - Both Web (`ClientDetailDrawer.tsx` `cacheRef`) and Mobile (`clients.tsx` `mobileDetailCacheRef`) store tab responses in memory.
   - Re-clicking previously visited tabs restores records in **0.0006ms – 0.0016ms** with 0 network calls and 0 database queries.
6. **Cross-Platform Mobile Parity**:
   - Mobile app (`apps/mobile/app/(app)/clients.tsx`) provides Client Detail Modal with touchable card header, dedicated `Details` action button, full 9-section hierarchy, horizontal scrollable tab strip, and min 44px touch targets.

## 7. Progressive Location Hierarchy Optimization (Milestone C14)
- **Problem**: Master location dataset contains 657,154 records (36 states, 784 districts, 466 cities, 15,081 towns, 640,787 villages). Streaming the full dataset to the client would require ~53.27 MB of JSON payload.
- **Progressive Cascade Architecture**:
  ```text
  State (36 records, ~1.07 KB)
    ↓ user selects state
  District (~34 records, ~1.43 KB)
    ↓ user selects district
  City / Town (~9 records, ~0.42 KB)
  ```
- **Zero Full-Hierarchy Serialization**: Clients receive strictly ~1 KB per selected slice, achieving **99.99% wire payload reduction** (2.92 KB transferred vs ~53 MB).
- **Multi-Tier Caching**:
  - Server-side: 24-hour static cache (`unstable_cache`, `CACHE_TIERS.CLASS_A_STATIC`, tag: `TAGS.clientsLocations`).
  - Client-side: In-memory `sessionCacheRef` / `mobileLocationHierarchyCacheRef` delivering **0ms re-toggles (<0.002ms)** with 0 database queries.
- **UI Integration**:
  - `ClientModal.tsx`: Standardized manual address fields strictly following canonical order (`street/area -> city/town/village -> district -> state -> pincode`) for both Site Location and Billing Address with uniform `<Input>` component sizing/padding. Includes card-level hover triggers (`data-hover-parent`) animating `AnimatedBuilding2`, `AnimatedMapPin`, and `AnimatedReceipt`.
  - `ClientStatusTabs.tsx`: Supports filtering by location with MapPin indicator.
  - `apps/mobile/app/(app)/clients.tsx`: Standardized manual address fields matching canonical ordering and min 44px touch targets.
- **Search Support**: Accelerated full-text search across `city`, `district`, and `state` via PostgreSQL GIN trigram indexes (`idx_clients_city_trgm`, `idx_clients_district_trgm`, `idx_clients_state_trgm`).

## 8. Action Menu & Deactivation / Soft Delete Flow (Milestone C15)
- **Zero Data Preloading on Action Menu Open**:
  Opening the action menu (`⋮`) is purely a local client UI layout/coordinate event (< 1ms). Issues strictly 0 network requests, 0 database queries, and loads 0 cascading deletion/impact data.
- **Strict JIT Lifecycle**:
  ```text
  Click Delete
       ↓
  load confirmation dialog (ClientDeleteModal)
       ↓
  confirm
       ↓
  server mutation (deactivateClient / softDeleteClientAction)
       ↓
  targeted invalidation (detail + list + KPI)
  ```
- **Zero Full-Page Reload**:
  `window.location.reload()` is strictly eliminated. Upon successful deletion or restoration:
  - Local `clients` state is updated immediately in memory (filtering out soft-deleted item or updating status).
  - Total count is decremented/updated.
  - In-memory `queryCacheRef` is cleared.
  - Silent `router.refresh()` in background keeps server components fresh without blocking the interactive UI.

## 13. Security, RBAC & Cache Isolation (Milestone C20)
- **Enforced Roles**:
  - Full Access: `super_admin`, `admin`, `manager`, `service_manager`.
  - Operational Scope: `supervisor`.
  - Strictly Prohibited: `operator`, `mechanic`, `engineer`.
- **Server Action Gatekeeping**:
  `getClientListAction`, `searchClientsAction`, `getClientDetailAction`, and all detail sub-actions verify user role via `getCurrentUser()` and block unauthorized roles with explicit 403 errors.
- **Cache Key Isolation**:
  Cache keys incorporate user scope, branch, and filter parameters to guarantee User A never receives User B's cached records.

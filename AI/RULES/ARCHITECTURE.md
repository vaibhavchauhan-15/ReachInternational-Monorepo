## 4. Monorepo Architecture

### Workspace Tools
* **Package Manager**: `pnpm` (v11.21.0). All dependencies MUST be installed using `pnpm`. Standard `npm` or `yarn` lockfiles are prohibited.
* **Build System**: `Turborepo` (v2.10.11). Pipelines are orchestrated in `turbo.json`:
  * `build`: Topological execution (`^build`), outputs `.next/**`, `dist/**`.
  * `typecheck`: Topological compilation check (`^typecheck`).
  * `lint`: Code quality check (`^lint`).
  * `dev`: Uncached persistent local dev server.

### Workspace Protocol
Dependencies between monorepo packages MUST use explicit workspace protocols (`"workspace:*"`). Hardcoded version strings for internal packages are forbidden.

## 5. Application Boundaries

1. **`apps/web` (`@reachinternational/web`)**:
   * Desktop & Tablet Enterprise Portal built on Next.js 16.2 App Router.
   * Leverages React Server Components (RSC) for initial page loads and Data Access Layer (DAL) reads.
   * Uses Next.js Server Actions (`app/actions/*`) for all state mutations.
   * NEVER exposes raw client-side database connections for mutations.

2. **`apps/mobile` (`@reachinternational/mobile`)**:
   * Field Engineer & Operations mobile application built on Expo 54 and React Native 0.81.
   * Consumes `@reachinternational/api-client` and `@tanstack/react-query` for client-side data fetching.
   * Manages authentication via Supabase JS client with custom native secure storage persistence.

3. **Strict Boundary Rule**:
   * `apps/web` and `apps/mobile` are sibling applications.
   * **CROSS-APP IMPORTS ARE FORBIDDEN**: Code in `apps/web` MUST NEVER import from `apps/mobile` and vice-versa.
   * Shared logic MUST be extracted into a package inside `packages/*`.

## 7. Dependency Direction

Dependencies MUST flow in a Directed Acyclic Graph (DAG) in **ONE DIRECTION ONLY**:

```text
Applications Layer (apps/web, apps/mobile)
       │
       ▼
Shared Domain Packages (@reachinternational/validation, permissions, api-client, design-tokens)
       │
       ▼
Foundation Packages (@reachinternational/types, utils)
```

### Dependency Rules:
1. **Forbidden Upward Dependencies**: `packages/*` MUST NEVER import from `apps/*`.
2. **Forbidden Cross-Layer Dependencies**: Foundation packages (`types`, `utils`) MUST NEVER import from Shared Domain packages (`validation`, `permissions`, `api-client`).
3. **Forbidden Circular Dependencies**: Direct or indirect circular dependencies between packages are strictly prohibited.
4. **Canonical Barrels Only**: Imports from workspace packages MUST always target the canonical package root barrel (`index.ts`). Deep internal path imports (e.g., `@reachinternational/types/src/database.ts`) are **FORBIDDEN**. Use `import { ... } from "@reachinternational/types"`.

## 10. Server vs Client Boundaries

Next.js 16.2 requires rigorous separation of Server and Client execution contexts:

### Server Components (`RSC`) — DEFAULT CHOICE
* All pages (`page.tsx`) and layout wrappers (`layout.tsx`) MUST be Server Components by default.
* **Responsibilities**: Fetch data via DAL (`lib/dal.ts`) or query modules (`lib/queries/*`), enforce server-side auth redirect, render initial HTML shell, stream heavy content.
* **Forbidden**: Cannot use React hooks (`useState`, `useEffect`, `useRouter`), browser event listeners, or client interactivity.

### Client Components (`'use client'`)
* Declared explicitly with `'use client'` directive at the top of the file.
* **Justified Scenarios**:
  1. Interactive form controls, modals, tabs, drag-and-drop elements.
  2. Canvas/SVG widgets (e.g. `CustomTimePicker.tsx`, `Recharts` graphs).
  3. Browser events, local state management, toast triggers.
* **Rules**:
  * Keep Client Components as leaf nodes low in the component tree.
  * Pass server data down to Client Components as serializable props.
  * NEVER convert a page or layout into a Client Component just to access a hook; extract the interactive element into a dedicated component file.

## 11. Data Access Architecture (DAL)

All server-side data fetching and authorization checks MUST pass through the canonical **Data Access Layer**:

```text
Page / Server Component
       │
       ▼
lib/queries/[domain].ts  (e.g., lib/queries/machines.ts)
       │
       ▼
lib/dal.ts  (verifySession / requirePermission / getUserBranchIds)
       │
       ▼
lib/supabase/server.ts  (Supabase SSR Server Client with user context)
       │
       ▼
Supabase PostgreSQL Database (Enforces RLS)
```

### DAL Rules (`apps/web/lib/dal.ts`):
1. **`verifySession()`**: Authenticates the incoming request session token. Redirects unauthenticated requests to `/login`. Wrapped in React `cache()`.
2. **`getCurrentUser()`**: Retrieves the full profile of the logged-in user from `public.users` table, including assigned `branch_id`. Uses `unstable_cache` with `CACHE_TAGS.users` revalidation.
3. **`requirePermission(code)`**: Verifies if the current user role possesses the specified RBAC permission code via `@reachinternational/permissions`. Redirects unauthorized users to `/dashboard`.
4. **`requireRole(...roles)`**: Restricts access to specific role enums. (`super_admin` automatically bypasses role restrictions).
5. **`getUserBranchIds()`**: Computes accessible branch IDs for multi-tenant / branch-scoped queries (`null` = unrestricted for `super_admin`).

### Query Rules (`apps/web/lib/queries/*.ts`):
* Queries MUST be server-only functions (`import "server-only"`).
* Direct database queries inside page files or UI components are **STRICTLY FORBIDDEN**. All data retrieval MUST be encapsulated in `lib/queries/*.ts`.

## 12. Database Architecture (Supabase PostgreSQL)

ReachInternational uses Supabase PostgreSQL as its single source of truth.

### Database Schema & Types
* Database tables, functions, triggers, and RLS policies are maintained via SQL migration files in `supabase/migrations/` (e.g. `001_initial_schema.sql` to `035_operator_log_direct_store_auto_approval.sql`).
* TypeScript database types are maintained in `@reachinternational/types` (`src/database.ts`).
* **Rule**: When adding or altering database tables or columns, AI agents MUST create a new migration SQL file in `supabase/migrations/` and update `@reachinternational/types/src/database.ts`.

### Supabase Client Selection:
1. **`createSupabaseServerClient()`** (`lib/supabase/server.ts`): Uses user session cookies. **Use for 95% of queries & mutations** so Postgres RLS is respected.
2. **`createSupabaseAdminClient()`** (`lib/supabase/admin.ts`): Uses `SUPABASE_SECRET_KEY` (service role). Bypasses RLS. **FORBIDDEN IN CLIENT COMPONENTS**. Restricted strictly to DAL internal profile lookups, cron workers (`app/api/cron/*`), and system-level administrative tasks.
3. **`createSupabaseBrowserClient()`** (`lib/supabase/browser.ts`): Used in browser client components when direct realtime subscriptions are required.

## 13. Authentication Architecture

Authentication is powered by Supabase SSR Auth (`@supabase/ssr`).

```text
Browser Request
       │
       ▼
apps/web/proxy.ts (Edge Auth Proxy)
       │ Check session cookie
       ├─────────────────────────────────┐
       ▼ (No Session)                    ▼ (Valid Session)
Protected Route?                     Public Route or Root '/'?
       │                                 │
  [Redirect to /login]              [Redirect to /dashboard]
```

1. **Proxy Protection (`apps/web/proxy.ts`)**: Next.js edge proxy intercepts all incoming requests matching protected routes (`/dashboard`, `/machines`, `/services`, `/users`, `/notifications`, etc.). Validates session tokens and executes edge redirects.
2. **Server-Side Session Verification**: Server Components and Server Actions call `verifySession()` or `getCurrentUser()` from `lib/dal.ts`.

## 14. Authorization & RBAC Architecture

Authorization enforces fine-grained Role-Based Access Control (RBAC) across 13 enterprise roles:

### Supported Roles:
1. `super_admin` / `admin`: Full system access across all organizations and branches.
2. `service_manager`: Manages assigned client accounts, machine schedules, FSRs, and engineers.
3. `engineer` / `mechanic`: Field operations, logs machine services, submits FSR reports.
4. `client`: Read-only / self-service view of owned machines, service history, and invoices.
5. `store_manager`, `branch_manager`, `supervisor`, `operator`, `hr_manager`, `rental_manager`, `sales_manager`, `finance_manager`: Operational domain managers.

### 3-Tier Scoping Rules:
* `global`: System-wide access (Super Admin).
* `branch_scoped`: Operations restricted to user's assigned `branch_id` (evaluated via `getUserBranchIds()`).
* `assigned`: Access restricted to records directly assigned to the user (e.g. engineer assigned to service ticket).
* `client_own`: Access restricted strictly to client's owned organization.

### Dual-Layer Security Boundary:
1. **Application Layer**: Enforced in Server Actions & DAL queries using `requirePermission(code)` from `@reachinternational/permissions`.
2. **Database Layer**: Enforced in PostgreSQL using Row Level Security (RLS) policies (`supabase/migrations/*.sql`) evaluating `auth.uid()` and `users` table metadata.

## 17. API Architecture

1. **Server Actions (Primary Web API)**: Form submissions and UI mutations MUST use Server Actions placed in `apps/web/app/actions/`.
   * Must include `'use server'` directive.
   * Must enforce `requirePermission()` or session check.
   * Must validate inputs via Zod schema (`@reachinternational/validation`).
   * Must write audit logs (`lib/audit-helpers.ts`) for all data modification events.
   * Must return standardized result object: `{ success: boolean; data?: T; error?: string }`.
2. **API Routes (`apps/web/app/api/`)**: Restricted to edge webhooks, background cron triggers (`/api/cron/*`), and external integration handlers.
3. **API Contracts (`@reachinternational/api-client`)**: Shared HTTP contracts used by Mobile app and external consumers.

## 18. Validation Architecture

1. **Canonical Schema Repository**: All Zod validation schemas MUST reside inside `@reachinternational/validation` (`packages/validation/src/`).
2. **Reuse Across Layers**: The same Zod schema MUST be used in:
   * Client-side form validation (e.g. `react-hook-form` / custom form state).
   * Server Action parameter validation.
   * Mobile API mutation payload validation.
3. **No Duplicate Schemas**: AI agents MUST NOT create inline ad-hoc Zod schemas inside UI components or Server Actions when a canonical schema exists in `@reachinternational/validation`.

## 19. State Management Architecture

* **Server State (Web)**: Managed via Next.js RSC, DAL queries, and `revalidateTag` / `revalidatePath` inside Server Actions.
* **Server State (Mobile)**: Managed via `@tanstack/react-query` using Query Keys defined in `@reachinternational/api-client`.
* **URL Search State**: Web navigation, view filters, pagination, and sub-tab selections (e.g. `/dashboard?tab=entry` vs `/dashboard?tab=history`) MUST be driven by URL search parameters (`useSearchParams` / `useRouter`).
* **Local Component State**: React `useState` / `useReducer` reserved strictly for transient UI toggles (modals open/close, dropdown states, local input buffers).

## 22. Error Architecture

3. **UI Error Boundaries**: Web App uses root `not-found.tsx` and route-level error boundaries to gracefully render error cards conforming to `DESIGN.md`.

## 25. Architectural Invariants (NEVER VIOLATE)

The following 8 rules are **ARCHITECTURAL INVARIANTS**. No AI agent has authorization to violate these rules under any circumstances:

1. **DAG Dependency Order**: `apps/*` → `shared domain packages` → `foundation packages`. No upward, cross-app, or circular dependencies.
2. **Canonical Barrel Imports**: Import strictly through canonical package barrels (`index.ts`). Deep imports into package internal paths are prohibited.
3. **Server Actions for Mutations**: All database writes/updates MUST go through Server Actions (`app/actions/*`). Client-side direct database mutations are forbidden.
4. **DAL for Data Access**: Server Data fetching MUST use `lib/dal.ts` or `lib/queries/*`. Direct raw SQL or un-cached client-side DB calls on the server are forbidden.
5. **No Secret Key Exposure**: `SUPABASE_SECRET_KEY` and `createSupabaseAdminClient()` MUST NEVER be imported into Client Components or exposed to the browser.
6. **Strict DESIGN.md Adherence**: UI implementations MUST strictly conform to `DESIGN.md` Vercel Geist design tokens (`#171717` ink, `#fafafa` canvas, `#ffffff` elevated, `#ebebeb` hairline border, `#0070f3` link blue).
7. **3-Tier Viewport Responsiveness**: Every layout MUST be optimized for Mobile (≤640px touch cards `block sm:hidden`, scroll toolbars), Tablet (641px–1023px 2-col grids), and Desktop (≥1024px data tables `hidden sm:block`).
8. **Memory & README Synchronization**: After completing any implementation, AI agents MUST update `AI/STATE.md`, `AI/CURRENT_TASK.md`, `AI/CHANGELOG_AI.md`, and `README.md`.

## 26. Forbidden Anti-Patterns

AI agents MUST NEVER introduce any of the following anti-patterns:

* ❌ **Direct DB calls in Client Components**: Writing `supabase.from('machines').update(...)` inside a `'use client'` component.
* ❌ **Ad-hoc RBAC logic**: Hardcoding custom role checks inside UI components instead of using `@reachinternational/permissions` and DAL `requirePermission()`.
* ❌ **Deep Package Imports**: Writing `import { User } from "@reachinternational/types/src/database"`.
* ❌ **Cross-App Imports**: Writing `import { Header } from "../../apps/web/components/Header"` inside `apps/mobile`.
* ❌ **Ad-hoc Zod Schemas**: Creating duplicate Zod validation schemas in action files instead of placing them in `@reachinternational/validation`.
* ❌ **Unnecessary Component Conversion**: Adding `'use client'` to an entire page component just to access `useState` or `useSearchParams`.
* ❌ **Bypassing RLS with Admin Client**: Using `createSupabaseAdminClient()` for standard user query flows when `createSupabaseServerClient()` should be used.
* ❌ **Ignoring Responsiveness**: Building desktop-only data tables without mobile touch-card reflows (`block sm:hidden`).
